# Research crate modernization for cargo-modernize

This skill teaches a repeatable method for researching how Rust crates have modernized over time, compiling a comprehensive inventory, and identifying how to capitalize on a shared database of that information. It is designed for authors of `cargo-modernize` rules (`rules/*.toml`) and for anyone maintaining the `modernize-ecosystem` data.

## When to use

- You need to add or refresh `cargo-modernize` rules for a set of crates (upgrades, deprecations, std replacements).
- You want a comprehensive list of libraries the project is responsible for, with their modernization stories.
- You want to know how to leverage `rules/ecosystem.toml` (the generated shared database) alongside hand-written rules.

## Method overview

The method has five steps:

1. **Inventory the tracked crates** — read every `cargo-modernize/rules/*.toml` to list all hand-written libraries by category.
2. **Spawn parallel research sub-agents** — group crates by category (upgrade, deprecated/unmaintained, std replacement, chrono/ring) and dispatch one agent per group.
3. **Compile findings** — for each crate: current version, previous major versions, breaking API changes, migration path, RustSec status, successor recommendations, and official docs.
4. **Map to rules** — connect each finding to the specific `[[rule]]` in `cargo-modernize/rules/*.toml` that covers it.
5. **Shared-database strategy** — analyze `rules/ecosystem.toml` (generated by `modernize-ecosystem`) and identify how to capitalize on it (auto-generate rules, prioritize fixes, share across projects, scorecards).

## Step 1: Inventory the tracked crates

Read all of these files in `cargo-modernize/rules/`:

| File | What it covers |
|------|---------------|
| `upgrades.toml` | Major-version bumps with API breaks (dependency, path, method rules) |
| `deprecated.toml` | Unmaintained, deprecated, archived crates (dependency, macro, path rules) |
| `std.toml` | Crates upstreamed into std (pattern, path, macro rules) |
| `chrono.toml` | chrono deprecated APIs (method, path rules) |
| `ring.toml` | ring 0.16 → 0.17 and deprecated APIs (dependency, path, method rules) |
| `rusty.toml` | Idiom opinions, some path rules for std items (criterion, scopeguard, filetime) |
| `ecosystem.toml` | Generated database of 450+ crates with status, successors, std_successors |
| `edition.toml` | Edition migrations (no specific libraries) |
| `features.toml` | Feature gates (no specific libraries) |

For each rule, note: `id`, `kind`, `category`, `plan`, `crate`, `version`/`to_version`, `paths`/`names`, `rename`/`replace_with`, `message`, `docs`, `fix` (safe/dangerous), `since_rust`.

Build a master list grouped by category:

### Category A: Upgrade rules (major-version bumps)
From `upgrades.toml` — 8 crates, 12 rules:

| Crate | Current version | Previous major | Key migration |
|-------|----------------|----------------|---------------|
| thiserror | 2.0.21 | 1.x | Raw identifier `{r#type}` → `{type}`; direct dep required; optional `std` feature |
| syn | 3.0.9 | 2.x | `Type::BareFn` → `Type::FnPtr`; `Punctuated::pop` → `Option<T>`; many syntax-tree renames |
| clap | 4.6.7 | 3.x | `#[clap]` → `#[arg]`/`#[command]`; `App` → `Command`; `with_name` → `new` |
| bitflags | 2.13.2 | 1.x | Explicit trait derives; `.bits()` / `from_bits_retain()` |
| hyper | 1.12.0 | 0.14 | `Body` is a trait; `Client`/`Server` in `hyper-util` |
| tokio | 1.54.1 | 0.x | `delay_for` → `sleep`; `threaded_scheduler` → `new_multi_thread` |
| base64 | 0.23.1 | 0.21/0.20 | Free functions → `Engine` API (`STANDARD.encode()`) |
| rand | 0.10.3 | 0.9/0.8 | `thread_rng()` → `rng()`; `gen` → `random`; `distributions` → `distr` |

### Category B: Deprecated / unmaintained crates
From `deprecated.toml` — 15 crates, 16 rules. Each has a status, RustSec ID(s), and primary replacement.

### Category C: Std replacements
From `std.toml` + `rusty.toml` — 17 crates/patterns. Each has a std replacement, stabilization Rust version, and migration mapping.

### Category D: chrono and ring
From `chrono.toml` (4 rules) and `ring.toml` (5 rules).

### Category E: Generated ecosystem database
From `ecosystem.toml` — 450+ crates with `latest`, `last_release`, `status`, `evidence`, `advisories`, `std_successors`, `successors`.

## Step 2: Spawn parallel research sub-agents

Dispatch 3–4 sub-agents in parallel, one per category group. Each agent should receive:

- The list of crates in its group
- The specific rule(s) from `cargo-modernize/rules/*.toml` that cover each crate
- The questions to answer (see "Per-crate research questions" below)

Example sub-agent prompts (adapt to your crate list):

**Upgrade crates agent:**
> Research these crates: thiserror, syn, clap, bitflags, hyper, tokio, base64, rand. For each: current stable version, previous major versions, key API changes/breaking changes, migration path, deprecation/security/unmaintained status, and official docs URLs. Return detailed findings per crate.

**Deprecated crates agent:**
> Research these crates: error-chain, failure, structopt, tempdir, memmap, dotenv, ansi_term, yaml-rust, serde_yaml, proc-macro-error, instant, rustc-serialize, difference, paste, async-std. For each: status (unmaintained/archived/deprecated), deprecation date, RustSec ID(s), recommended replacement, API differences, and links.

**Std replacement agent:**
> Research these crates: lazy_static, once_cell, num_cpus, atty, is-terminal, crossbeam, byteorder, maplit, static_assertions, array_init, itertools, memoffset, matches, async-trait, criterion::black_box, scopeguard, filetime. For each: std replacement, stabilization Rust version, old crate last version, API mapping, migration example, links.

**chrono + ring agent:**
> Research chrono and ring. For each: current version, deprecated APIs and replacements, migration guidance, RustSec status, docs URLs.

## Step 3: Per-crate research questions

For every crate, answer these:

| Question | Why it matters |
|----------|---------------|
| Current stable version and release date? | Needed for `to_version` and currency checks |
| Previous major version(s)? | Defines the upgrade path the rule covers |
| Key API changes / breaking changes? | Drives `paths`, `names`, `rename`, `suggestion` fields |
| Migration path (code before/after)? | Becomes the rule's `suggestion`, `message`, and examples |
| Deprecation / unmaintained / archived status? | Determines `category` and `level` |
| RustSec advisory IDs? | Drives `deny` level for `vulnerable`/`yanked` |
| Recommended successor crate? | Populates `successors` in ecosystem data |
| Official docs / changelog URLs? | Goes in the rule's `docs` field |
| `since_rust` for the replacement? | Gates the rule against the crate's `rust-version` |

## Step 4: Map findings to rules

For each finding, identify which `[[rule]]` in `cargo-modernize/rules/*.toml` covers it, or whether a new rule is needed:

- **Dependency rule** (`kind = "dependency"`) — fires when the crate appears in `Cargo.toml` at a version matching `version`. Use for version bumps (thiserror → 2, rand → 0.10) and deprecation notices.
- **Path rule** (`kind = "path"`) — fires on resolved `use` paths or fully-qualified paths. Use for renamed items (`clap::App` → `Command`, `rand::thread_rng` → `rng`).
- **Method rule** (`kind = "method"`) — fires on `.name()` calls. Add `requires_import` to avoid false positives. Use for `gen` → `random`, `delay_for` → `sleep`.
- **Macro rule** (`kind = "macro"`) — fires on macro invocations by name. Use for `error_chain!`, `defer!`, `matches!`.
- **Pattern rule** (`kind = "pattern"`) — names a built-in structural detector in `PATTERNS` (src/scan.rs). Use for `lazy-static`, `crossbeam-scope`, `let-else`, etc.

For each rule, set:
- `category` — `upgrade`, `deprecated`, `std`, `edition`, `idiom`, `rusty`
- `level` — `deny`/`warn` for actionable; `suggest` for opinions; `off` to disable
- `fix` — `safe` if behavior-preserving, `dangerous` (default) if it may break compilation
- `since_rust` — the Rust version when the replacement stabilized
- `docs` — official changelog or migration guide URL

## Step 5: Capitalize on the shared database

The project already has a shared database: **`rules/ecosystem.toml`**, generated by `modernize-ecosystem` (runs weekly in CI via `.github/workflows/ecosystem.yml`). It tracks 450+ crates, each with:

```toml
[crates.<name>]
latest = "0.10.3"
last_release = "2026-09-20"
status = "unmaintained" | "deprecated" | "archived" | "yanked" | "vulnerable" | "at-risk" | "outdated" | "transitive"
evidence = ["RUSTSEC-XXXX-XXXX: ..."]
advisories = ["RUSTSEC-XXXX-XXXX"]
std_successors = ["std::io::IsTerminal"]   # std replacement, if any
[[crates.<name>.successors]]
name = "replacement-crate"
score = 85
recommended = true
why = ["named as an alternative in RUSTSEC-X", ...]
```

### How to capitalize on it

**A. Auto-generate hand-written rules from ecosystem data**
The 38 hand-written rules in `upgrades.toml`, `deprecated.toml`, `std.toml`, `chrono.toml`, `ring.toml` could be generated from or validated against `ecosystem.toml`:
- If `ecosystem.toml` marks `ring` as `unmaintained` with successor `ring 0.17`, the `ring/upgrade` rule could be auto-generated.
- If `ecosystem.toml` marks `atty` as `unmaintained` with `std_successors = ["std::io::IsTerminal"]`, the `std/atty-dep` rule could be auto-generated.
- Extend `modernize-ecosystem` to emit `[[rule]]` TOML for ecosystem-tracked crates without hand-written rules.

**B. Cross-reference hand-written rules with ecosystem successors**
When a hand-written deprecation rule exists (e.g. `deprecated/tempdir` → `tempfile`), the ecosystem database can confirm or update the successor recommendation. If `ecosystem.toml` lists a newer, higher-scored successor, cargo-modernize can suggest it alongside the hand-written rule.

**C. Use ecosystem scores to prioritize fixes**
The `successors` entries have `score` and `recommended` fields. cargo-modernize can:
- `deny`-level for `yanked` or `vulnerable` (already done via `ecosystem/yanked`, `ecosystem/vulnerable`)
- `warn` for `unmaintained` crates with a clear successor
- `suggest` for `at-risk` crates (already done)

**D. Share the database across projects**
Since `ecosystem.toml` is plain TOML, it can be:
- Version-controlled and shared between teams/orgs
- Overridden per-project via `--ecosystem FILE` or `CARGO_MODERNIZE_ECOSYSTEM` (supported in `cargo-modernize/src/ecosystem.rs`)
- Extended with project-specific rules via `.modernize` files (`[[rule]]` tables)

**E. Build a "modernization scorecard" per crate**
Compute urgency from ecosystem data:
- Time since `last_release`
- `status` (unmaintained > deprecated > archived > at-risk)
- RustSec advisory count
- Successor `score` and `recommended` flag
- `recent_downloads` (ecosystem.toml has this field)

This lets users see which dependencies need attention most urgently.

## Output format

Produce a structured report with these sections:

1. **Comprehensive library inventory** — master table of all tracked crates by category (current version, previous major, key migration, status).
2. **Modernization details per crate** — version history, breaking API changes, before/after code examples, migration guidance, RustSec IDs, docs URLs.
3. **Rule mapping** — each finding mapped to its `[[rule]]` in `cargo-modernize/rules/*.toml`, with any gaps where a new rule is needed.
4. **Shared-database strategy** — analysis of `ecosystem.toml` and concrete recommendations for auto-generating rules, prioritizing fixes, sharing across projects, and scorecards.

## Validation

- Verify each crate's current version against crates.io (or the project's `Cargo.lock` / `ecosystem.toml`).
- Check that every hand-written rule has a corresponding entry in the inventory.
- Confirm that `docs` URLs point to official changelogs or migration guides.
- Run `cargo test -p cargo-modernize` after adding or modifying rules.
- Validate on real code: run `cargo modernize` against a few large crates and check that hits are genuine.
